# 提示词重放实验：先验证，后接入

本实验只新增脚本和实验产物，不修改 `src`、已保存Agent/组或原始游戏记录。使用 unit test 原绑定的模型及各原请求实际参数，包括 `reasoning_effort=none`；不切换模型、不降低旁白温度来混淆效果。

## 实验变量

- baseline：逐条重发原 `resolvedMessages`。
- candidate：保留原请求全部非system消息，替换所有system提示词为角色专用的精简版本。要求先在内部完成三个关键核对，再仅输出原JSON；不增加长篇推理字段。
- 不向模型提供案例ID、失败标签、人工预期、评分理由或原模型答案。审查器本来要审阅的候选文本仍是它的原始输入。
- 同一案例每个版本各3次，交替版本顺序，两个请求并发。每次只发一次，禁用运行时格式重试。JSON协议与人工语义分开评定。
- 请求、参数、原证据、正式源代码保存指纹；原始输出与每次新回复都保留。新请求以临时角色ID避开正式运行时旧提示词的再次注入，只在进程内复制绑定，绝不保存到应用。

## 判定标准（运行前冻结）

人工审阅按 `cases.json` 中每个案例的预期检查关键含义和事实，并检查有无新的实质错误。不规定最终台词，不因风格、正常停顿或无事实后果的修辞判错。正常拒绝或有依据的角色不诚实不能一概当错。

同一角色只有在相关失败案例的candidate三次均修复、正确对照三次均保持正确、格式没有退化时，才具备进入管线验证的资格。旧提示词的同期回复用于区别随机波动与可重复改善；旧版本也全部通过的案例只能说本次未复现，不能把改善归功于新提示词。

三次重复只是有限证据，不是普遍正确性的证明。局部改善、有新错误或结果波动的角色保持实验状态，不以降低预期、挑最好一次或换模型宣布修复。不根据独立审查Agent自己说“通过”推断它检测正确。

本轮首先隔离“system提示词替换”这一变量；若仍失败，再单独试输入去重/紧凑事实展示，不能把两个改动混在一起却声称知道是哪一个起作用。正式接入之前需要针对获准角色的管线验证，已有结构和安全门禁保持不变。
