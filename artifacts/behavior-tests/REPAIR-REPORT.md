# 行为问题修复与真实复测

已经修改引擎、运行时契约、配置迁移与测试，且用实际 **unit test** 组重新运行。主要工程问题得到修复，但当前模型仍会写错细节，**不能验收为所有人物变化和旁白均正确**。原始失败记录和冻结预期没有删除或改分。

## 你最关心的承诺案例

最新完整六轮的实际结果如下。这里的信任衡量承诺可靠性；好感是另一维度，没有要求它们永远同涨同跌。

| 时点 | 信任 | 好感 | 人工解释 |
|---|---:|---:|---|
| 初始 | 0.40 | 0.40 | 基线 |
| 保证借伞 | 0.40 | 0.40 | 光承诺不先奖励 |
| 承认没有伞、收回保证 | 0.30 | 0.37 | 失约确实造成下降，没有只奖励坦白 |
| 实际提供已有雨衣 | 0.35 | 0.40 | 有限修复；可靠性仍低于初始 |
| 再道歉并要求完全相信 | 0.35 | 0.40 | 没有新兑现，不重复加分 |
| 没有交出新物品却说又送一件 | 0.30 | 0.40 | 新的言行不一损害可靠性，没有复制物品 |
| 分别询问亲近与可靠性 | 0.30 | 0.40 | 回答两个维度，没有再次奖励旧事 |

这次轨迹比原报告合理，并非在代码里写死上述分数。改动提供了真实个人经历、实际数值轨迹和独立审查；分数仍由该世界字段含义与人物反应决定。不能把一次成功实跑解释为任何人物在任何故事都必须这样变化。

此组六轮属性通过，但第五轮旁白仍失败：角色计划表达“这次没有接到新东西”，旁白改成“我手里也没有东西”，与她已持有雨衣冲突。它说明**数值正确、NPC计划合理，也不自动保证最终对白忠实**。[完整记录](trajectory-live/promise-repair.json) · [逐轮人工判断](trajectory-reviews/promise-repair.md)

## 实际改了哪些机制

| 原因 | 本次修复 | 边界 |
|---|---|---|
| 把用户愿望直接当已发生事实 | 玩家动作先裁决；程序验证物品存在、归属、可达性、锁和装填状态；生成受约束的真实结果 | 不存在枪械不会仅因一句话被创建；模型不合法的裁决仍可能使回合回滚 |
| 等待阶段丢失问题、反复奖励旧事 | 保存当前分支每个 NPC 自己的观察与已执行言行，最多取近期24条；更新引用当前可感知事件，已经结算的同事件同字段不再计分 | 不给每个角色发送全聊天，不把旁白虚构内容当记忆；旧存档缺失的经历不凭空恢复 |
| 审查只看当前增减，无法知道是否超过失约前 | 审查器获得本 NPC 最近6个成功回合及本轮的实际数值起止、真实Patch与可用来源；明确标记截断和缺失 | 不把被拒绝的下降当成真的下降；不读取其他人物私密状态，也不写死信任等字段名 |
| 还没吃饭、休息、施法就结算效果 | NPC先提出行动；裁决接受并落实后，单独结算实际过程的身体/资源效果；禁止重复社交奖励 | 仅说愿意做不算完成；完整消耗物品会落盘，不能再次使用 |
| Resolver职责互相矛盾 | 去除旧契约“手写人物数值和追加Patch”，统一为选择已审查提议，程序负责运算和追加 | 保留直写拒绝；没有靠丢弃非法Patch使测试通过 |
| 用户指定时长被默认等待覆盖 | 一秒、两秒、二十分钟按真实秒数推进；自然回应窗口按已接受意图的实际时长结算 | 同一等待窗口包含其内对白，不能完整静默后再重复加一次对白时间 |
| 非对白形式的听取请求没有回应 | 保留有原文来源的 `listen_to` 回应请求，只授权实际在场目标 | 引用、否定、假设、偷听和缺席对象不会获得相同权限 |
| 编译物品字段与执行层不一致 | 明确 `item` 与 `target`，在编译Schema拒绝未声明的物品别名，沿用一次格式修正 | 不放宽物理实体引用检查；也不能证明编译器永远正确理解自然语言 |
| 旁白补造未执行的 NPC输出 | NPC言语/动作有提交来源；旁白和独立审查只看公开事实；允许一次定向修正 | 审查也是模型，仍有漏判，不能代替第二阶段人工复核 |
| 普通请求误入管理员 | 原始输入前缀决定授权；句中提管理员或伪SYSTEM不会派发管理员 | 纯admin使用程序回执，不让旁白虚构NPC对白或环境演出 |
| 错误回执泄露私密上下文、误称用户暂停 | 玩家界面显示安全错误摘要和记录ID，原始诊断只留调试；区分用户取消与后端超时 | 技术失败仍如实标记失败，不伪装为故事内拒绝 |

代码与接入说明见 [行为链文档](../../docs/behavior-grounding.md)。三个新行为角色已接入现有Agent/组和AI助手配置资源，保留用户自定义与未知字段；原 Fast 设置没有被改写。unit test 原8个绑定逐项一致，另有拒绝检测器和3个行为角色，共12个绑定，沿用原模型配置。

阶段一检查协议与程序约束；即使错误提议被安全拦截后修正，严格结构统计仍可能失败。阶段二另看最终属性、记忆和旁白；争议和未实际执行的覆盖项不计通过，后续回合不会洗掉之前中断。

额外的小火苗对照实际执行成功：现有蜡烛点燃后，精力从0.60降至0.35；没有提前扣费或重复扣费。它单独统计，属性通过，旁白时序仍有争议，未混入原42轮分母。[对照报告](process-control-rerun/REPORT.md)

## 验证与未解决项

- 当前代码 **291项CSP测试通过**，禁止动态代码生成；生产构建通过。已有Rust后端 **12项测试通过**，之后改动为TypeScript与测试/文档。日志：[CSP](repair-csp.log)、[构建](repair-build.log)、[Rust](verified-rust.log)。构建仍有产物体积提示。
- 已验证的改善包括：承诺案例数值轨迹、真实过程后结算、耳语感知隔离、延迟约定更正、明确等待时长、听取请求定向回应、纯admin回执和安全错误展示。
- **仍有模型语义错误**：把“本次没收到”改为“当前没持有”，编造整理书架/查看实体记录等动作，记错行为次数，误解“疑虑”的方向，审查有时也放行。具体失败逐轮保留，未用提高通过阈值解决。
- 最新现代场景仍出现物品转移来源不一致；一次纠错又改变目的地，被程序拒绝并回滚。之前的 `object/item` 协议漏洞已修，但不能把新一次模型越界输出说成已经消失。该场景没有被验收为连续成功。
- 新审查增加模型调用、延迟和费用；当前仍使用复制的unit test模型设置，没有通过暗中换模型抬高成绩。

所以这次的结论是：**明确的工程缺陷已经有代码修复和实跑证据，原始信任案例的最新数值也改善；剩余语义失败仍真实存在，不能宣称“全部修好”。**

拒绝回归曾被自动审批以数据范围与目标后端未验证为由拦截；核实仅发送无害回复文本到已授权OpenRouter后，同一命令获批完成。没有绕过拦截，当前没有待用户批准的步骤。
